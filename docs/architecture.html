PkgGuard on AWS

How a package goes from "someone typed install" to a verdict, on one serverless AWS stack. Press play by just watching: the diagram loops.

  1. 1A request comes in from the CLI, the AI agent or the website, and the cache is checked.
  2. 2Seen before? The answer comes straight back in milliseconds.
  3. 3Not seen? A scan starts through Step Functions.
  4. 4The scanner fetches the package, asks threat intel, reads the code and asks a model.
  5. 5The package is run in the sandbox: no internet, watched at the network and kernel level.
  6. 6What the sandbox saw is written to S3 through a private endpoint.
  7. 7The report goes to S3, the verdict to DynamoDB, and everyone after gets it instantly.

Why this design

Scan once, answer forever

DynamoDB keeps every verdict. The first person pays the minute-long scan, everyone after gets a millisecond answer.

Serverless, pay per scan

Lambda, Step Functions and Fargate cost nothing when idle. The sandbox only exists while a package is being run.

A cage with no way out

The sandbox VPC has no internet gateway and no NAT, DNS is allow-listed, and the task holds no AWS credentials at all. It only gets one-time links to hand its results back.

Proof, not guesses

The sandbox records network, process and file activity at the system-call level. If fake credentials we planted leave the box, that is evidence.

One stack, one file

Everything above is defined in a single SAM template, so the whole environment can be recreated or torn down with one command.

Cost guardrails

Scan concurrency is capped, the sandbox can be switched off, and a budget alarm emails before spend gets out of hand.

Every AWS service, and what it does here

Amazon API Gateway (HTTP API)The public front door. The CLI, the MCP tool and the website all call it.
AWS Lambda: APIAnswers lookups from the cache, checks batches of packages, serves reports, and starts a scan when a package is new.
Amazon DynamoDBThe verdict cache: one record per package version, plus daily counters. A package is scanned once, then served instantly.
AWS Step FunctionsRuns one scan per package with retries and a time limit, and records failures cleanly.
AWS Lambda: ScanThe scanner. Fetches the package from npm, asks threat intel, reads the code (static analysis), prepares dependencies and starts the sandbox.
Amazon ECS on AWS FargateRuns the sandbox: each package is installed and loaded in a fresh, locked-down container that is thrown away afterwards.
Amazon VPC + Route 53 DNS FirewallThe cage. No internet gateway, no NAT. DNS is allow-listed and everything else is blocked, so nothing can phone home.
VPC endpoints (S3, ECR, CloudWatch Logs)Private doors to the few AWS services the sandbox needs, and nothing else.
Amazon S3Stores full reports and the raw sandbox traces (what the package did at the network, process and file level).
Amazon ECRHolds the container images for the Lambdas and the sandbox.
Amazon BedrockThe reviewer model. Reads the evidence and the risky code and explains its verdict.
AWS Amplify HostingHosts the website.
Amazon CloudWatch LogsLogs for the API, the scanner and the sandbox.
AWS BudgetsEmails an alarm when spend passes the monthly budget.
Outside AWSThe npm registry (the package itself), OSV.dev and SafeDep (known-malware lists).
